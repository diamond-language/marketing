Open source, ready to install

Ruby's warmth.
Real types. Compiled speed.

Diamond keeps the syntax, blocks, and object model that make Ruby comfortable to write — then adds gradual, checked static types and compiles it all to a register-bytecode VM with inline caches and a JIT, instead of walking a tree.

class Counter
  include Comparable

  def initialize(value: Int)
    @value = value
  end

  def <=>(other: Counter)
    @value <=> other.value()
  end
  def value() = @value
end

Where it actually differs

Familiar enough to skim, strict enough to trust

Diamond borrows Ruby's object-model ideas — it isn't a compatibility project. Matching Ruby's standard library or gem ecosystem is explicitly not a goal.

Every call needs parentheses

puts("x"), not puts "x"; Foo.new(), not Foo.new. No bare-call form, no ambiguity about what's being invoked.

Types are optional, but real

Annotations, union types with nil narrowing, generics, and structural interfaces (no implements — any matching class satisfies one) are checked at compile time, not just documented.

Compiled, not just interpreted

A Pratt compiler emits register bytecode for a VM with inline caches, object shapes, and quickening. diamond build produces a standalone native executable — no interpreter needed at runtime.

No shared mutable state

Threads use isolated heaps; values copy across boundaries. A Channel gives threads an ongoing mailbox, and a Supervisor restarts a crashed worker automatically — Erlang's one_for_one, not exception handling.

Sandboxing built into the language

diamond --sandbox denies filesystem, network, and subprocess access for running untrusted code — checked at each opcode, not bolted on with a wrapper.

No general eval

ClassName.compile_method compiles a capture-free method body from a source string — there's no arbitrary code evaluation in the calling scope.

See it in action

The same language, five angles

Classes and mixins, generated structs, exhaustive pattern matching, real OS threads and cooperative fibers, and a sandboxed runtime.

point.di
struct Point(x: Int, y: Int)
end

p1 = Point.new(1, 2)
p2 = Point.new(x: 1, y: 2)
p1 == p2               # true
p1.to_s()              # "Point(x: 1, y: 2)"

# initialize/readers/==/to_s are generated -- gradual
# types and nil narrowing work the same as anywhere else
def choose(flag: Bool, value: Point | Nil) -> Point | Nil
  if flag
    value
  else
    nil
  end
end

struct Name(field: Type, ...) ... end generates initialize, readers, ==, and to_s — and still composes with include, hand-written methods, and union types.

classify.di
def classify(value: Int) -> String
  case value
  when 0
    "zero"
  when 1, 2, 3
    "small"
  when 4..10
    "medium"
  else
    "large"
  end
end

Matching over a union or a sealed class hierarchy is checked for exhaustiveness at compile time — an uncovered case is a compile error, not a runtime surprise.

workers.di
# Thread: real OS threads, each with its own isolated
# heap -- runs in parallel across CPU cores

def square(n) = n * n

left = Thread.new(square, 6)
right = Thread.new(square, 7)
left.join()   # => 36
right.join()  # => 49

# Channel: an ongoing mailbox between isolated-heap threads
ch = Channel.new(64)
worker = Thread.new(producer, ch)
item = ch.receive()
worker.join()

# Supervisor: restart-on-crash, Erlang's one_for_one
sup = Supervisor.new()
sup.add_child(fetch_loop, "https://example.com/feed")
# a raise in fetch_loop restarts just that worker --
# siblings, and everything they hold, are untouched

Every value crossing a thread boundary is copied, never shared — no locks, no data races by construction.

counter_fiber.di
def make_counter()
  def counter()
    i = 0
    loop do
      increment = Fiber.yield(i)
      i = i + increment
    end
  end
  counter
end

counter = Fiber.new(make_counter())
counter.resume(0)     # => 0
counter.resume(10)    # => 10
counter.resume(5)     # => 15

Cooperative concurrency within a single OS thread — a fiber runs until it finishes or yields, never preempted in between. Reach for Thread instead when work should actually run in parallel across cores.

Install

Build it, run it, ship it

Diamond compiles from source today. Bytecode is cached automatically between runs, and diamond build produces a self-contained native binary when you're ready to ship. Pick your platform to get started.

Fedora is the maintainer's own dev machine and Ubuntu runs Skindicate in production, on top of both getting full CI coverage. macOS, Alpine, and FreeBSD are currently validated on GitHub Actions only — if you hit a problem there, please open an issue or a PR.

Ubuntu / Debian
# Install system dependencies
sudo apt install gcc libssl-dev libsqlite3-dev libpq-dev \
libmariadb-dev libcrypt-dev zlib1g-dev
# Build Diamond
make
macOS
# Install system dependencies (Clang only -- no system GCC)
brew install openssl@3 sqlite postgresql@16 mariadb-connector-c
# Build Diamond
make
Fedora
# Install system dependencies
sudo dnf install gcc openssl-devel sqlite-devel libpq-devel \
mariadb-connector-c-devel libxcrypt-devel zlib-devel
# Build Diamond
make
Alpine
# Install system dependencies (musl -- also needs libucontext)
apk add gcc musl-dev openssl-dev sqlite-dev libpq-dev \
mariadb-connector-c-dev zlib-dev libucontext libucontext-dev
# Build Diamond
make
FreeBSD
# Install system dependencies
pkg install gmake sqlite3 openssl postgresql16-client mariadb-connector-c
# Build Diamond (FreeBSD's GNU Make is gmake, not make)
gmake
run & ship -- same on every platform
# Run a one-liner
./build/diamond -e '20 + 22'
# => 42
# ...or run a file
./build/diamond program.di
# ...or start the REPL
./build/diamond
# Ship a standalone binary -- no interpreter needed at runtime
./build/diamond build app.di -o app
./app
